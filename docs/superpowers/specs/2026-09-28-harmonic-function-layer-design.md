## 1. 问题陈述（来自第 1 轮的实测，不靠猜）

第 1 轮接线循环锁死断路器后，真实 Jev 渠道的 `unique_chords` 仍停在 6-7。当时的结论是：

> `unique_chords` 停在 6-7 是**曲风词汇上限**——romantic 小调的进行池只有 i/bVI/bIII/bVII/iv/V 六个根音，模型能选的合法和弦本来就那么几个。

代码证据（`candidates.js` 的 `chordCandidates`）：

```js
for (const pool of pools) {          // pools = style.progs[mode]，每条只有 4 个罗马数字
  for (const sym of pool) { ... cand.set(s, ...) }   // 候选全集 = 所有 pool 的并集
}
```

候选全集**严格等于进行池的并集**。romantic 小调 4 条 pool 共 {i, bVI, bIII, bVII, iv, V} → 6 个根音 → `unique_chords` 天花板约 6-8，与调参无关。

**因此本轮要解决的是一个架构问题：候选集的来源太窄。**

同时，这是一个「让 Jev 做更聪明的事」的机会——第 7 问的引入方式决定了它是不是真创意。

## 2. 创意核心

> **在「罗马数字」和「模型」之间插入一层「和声功能」语义，并让 Jev 显式地为下一小节选择功能。**

三层结构：

```text
乐理层 music.js     调式音阶 → 全调内和声色板（diagonal palette）
功能层 candidates.js T / S / D / Tp 四功能 + 功能转移矩阵 + 共同音加权
模型层 composer.js   Jev 第 7 问「下一小节要哪个功能」；和弦仍在候选集内选
```

### 2.1 算法：共同音 + 五度圈距离

选一个后继和弦 C（当前和弦为 K）时，两条可量化的和声学信号：

| 信号 | 定义 | 音乐学含义 |
|---|---|---|
| `commonTones(C, K)` | `|chordPcs(C) ∩ chordPcs(K)|` | 共音越多，声部越平滑 |
| `fifthsDist(C, K)` | 根音在五度圈上的环形距离（0..6） | 五度圈上相邻=平滑，相邻大小三和弦=易转 |

```
smoothness = commonTones × 1.0 − fifthsDist × 0.25
```

这是经典的「五度圈进行生成」思路（Rochette 一脉）：不是拍脑袋给权重，而是从**声部进行的物理代价**推权重。它是本轮可称为「奇妙算法」的部分，且完全确定、可单测。

### 2.2 算法：功能转移矩阵

大调：`T→{S,D}`、`S→{D,Tp}`、`D→{T}`、`Tp→{D,T}`
小调：`T→{S,D}`、`S→{D,Tp}`、`D→{T}`、`Tp→{D,T}`（`Tp` = 离调色彩和弦，承担 ii°/iv/Neapolitan 的角色）

乐句尾强制 D→T 的权重抬升；乐句头偏好 T。

### 2.3 Jev 侧的用法（第 7 问）

**关键设计决策**：第 7 问**不做硬过滤**。理由见 §4 的方案对比——硬过滤会与「同一请求内无法先问功能再问和弦」冲突，导致合法作答被自己的前置问题判死。

实际用法是三件事，全部安全且各有价值：

1. **语义辅助**：让模型先说「下一小节要属功能」，和弦选择就在这个语境里发生（chain-of-thought 式的结构化提示）。
2. **更好的回落**：模型和弦作答非法时，不回落到「全局最高权重」，而回落到**「声明功能族内权重最高」的候选**。这是比原来更聪明的兜底——模型已经用一句话告诉了我们要往哪走。
3. **UI 轴**：决策日志多一列「功能」，是比罗马数字更有意义的可读维度（第 3 轮前端打磨直接可用）。

## 3. 方案对比（brainstorming 的批准门替代物）

| 方案 | 内容 | 取舍 | 结论 |
|---|---|---|---|
| **A. 纯扩池** | 手工把 `STYLES[*].progs` 写长（每条 8 和弦） | 最快；但要动 `STYLES`，被 `theory.test.mjs` 全量断言；且是拍脑袋词汇，8 种曲风 × 多调式 = 几十条手写，易腐化 | ✗ |
| **B. 生成式色板 + 共同音加权**（采纳） | 色板由调式音阶推导；权重来自功能转移 + 共同音 + 五度圈 + 进行延续 | 词汇量自动随调式增长，无需手写；权重有音乐学依据；纯函数可单测；不动 `STYLES` | ✓ |
| **C. Markov 转移矩阵拟合** | 从既有 pool 学转移概率 | 数据量太小（每曲风 4 条 pool），过拟合且不可解释；且仍是「池内」转移，解不了色板窄的问题 | ✗ |

**功能层（第 7 问）的三个子方案：**

| 子方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| C1. 硬过滤 | 模型答功能 → 和弦候选只留该族 | 同一请求内和弦问题已发出，模型看不到过滤结果 → 合法作答会被自己的前置问题判死。**逻辑自相矛盾** | ✗ |
| C2. 预过滤 | 发请求前用**期望功能**（弧线/乐句位置推出的确定性期望）过滤和弦候选 | 功能与和弦都由代码决定，模型对功能没有发言权 → 违背 ADR-0001「模型只做选择」 | ✗ |
| C3. 语义提示 + 智能回落 + UI 轴 | 不过滤；功能只用于（1）提示语境（2）非法作答时在功能族内回落（3）UI | 零风险、不违背任何 ADR、有真实增量价值 | ✓ |

## 4. 数据流

```text
nextBar()
  ├─ curFn = currentSymRoman ? functionOf(currentSymRoman, mode) : 'T'
  ├─ fnCands = functionCandidates(plan, curFn, isPhraseEnd)        // T/S/D/Tp 权重
  ├─ cands   = chordCandidates(..., recentRoots, fatigue)          // 全调内色板 + 两条断路器
  ├─ questions = { function(新), chord, lh, rhythm, contour, intensity, breathe, develop }
  ├─ 真实/fixture 决策
  ├─ 解析：picked = cands.find(...)；非法 → 声明功能族内最高权重 → 全局最高权重
  └─ decision.fn / decision.chordFn / decision.fnRejected / decision.rejected
```

## 5. 不变量与护栏

| 不变量 | 由什么保证 |
|---|---|
| 非法和声不可表示 | 色板全部来自调式音阶 + `parseRoman` 可解析；替换和弦走 `parseRoman` 校验 |
| 播放永不中断 | 三级回落链，末端必然是合法候选（`cands[0]`） |
| fixture 与真实同构 | 第 7 问也带 `_fixture.weights`，与 criteria 同源 |
| 候选集非空 | 沿用第 1 轮修好的 `out.length < 3` 三段兜底 |
| **不碰 `STYLES`** | 色板由 `SCALES` 推导；`theory.test.mjs` 的全量断言保持有效 |
