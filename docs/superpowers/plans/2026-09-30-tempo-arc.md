# 速度弧线（段落级 ritardando / 推进感）Implementation Plan

> **轮次 20 · 创意**（接续 2026-09-28 的 19 轮迭代；本轮起轮换顺序为 创意→前端→优化）
> **执行方式**：本会话内联执行（用户明确要求不使用子代理）。

**Goal**：整曲目前从头到尾一个速度——Coda 与 A 段用同一个 BPM 演奏。「结尾渐慢」是真人钢琴家最基本的呼吸，段落间的推进感（accelerando）也完全缺失。本计划给**时间维度**补上与张力弧线同级的段落语义：B 段轻微推进，尾段 ritardando 收束。

**Architecture**：纯渲染层改动，**不触碰 Jev 决策**（七问契约、候选集、权重全部不动）：
1. `candidates.js` 新纯函数 `tempoMultAt(plan, bar)` → 每小节一个速度乘数（小节内恒速，clamp 0.8..1.04）。
2. `player.js` `_enqueueBar` 从「恒定 secPerBeat × 绝对拍」改为**顺序游标累计**（每小节用自己的乘数）。
3. `midi.js` `exportMidi` 接受 `tempoMults`，在 track0 按小节写 SMF `set_tempo` 事件。
4. `main.js` / `studio.js` 导出 MIDI 时传乘数序列。

**Tech Stack**：原生 ES Modules、`node --test`、零依赖。

---

## 方案对比（brainstorming 结论）

| 方案 | 思路 | 取舍 |
|---|---|---|
| **A. 小节级乘数 + 顺序游标（采纳）** | 每小节一个恒定乘数，Player 逐小节累计秒 | 纯函数可测；决策零耦合；相邻小节差 ≤4% 时小节内的连续变化不可闻，粒度足够 |
| B. 连续 tempo 曲线（bar 内插值） | beat→sec 需要逐段积分 | 映射复杂、暂停/恢复/乱序都要重新推导，测试重、收益边际 |
| C. 只做 Coda 渐慢（最小实现） | 尾段乘数 <1 | 丢掉段落推进感，曲式的「时间形状」仍不完整 |

**采纳 A 的关键论据**：张力弧线已经段落化（轮次 8），但时间维度是死的——曲式有两根轴（响度 × 时间），现在只有一根在呼吸。A 方案把 `tempoMultAt` 做成与 `intensityTarget` 对称的纯函数，落在同一层（candidates.js，描述**计划**而非已生成音乐），心智模型一致。

## 设计细节

### `tempoMultAt(plan, bar)` → 0.8..1.04

- **最后一段**（`bars > 1`）：从段首 1.0 线性滑到段尾 **0.8**（rit.，90→72 BPM，真人尾声常见 −15%~−25% 取下沿）。用「最后一段」而非「id === 'Coda'」判断——LLM 的 sections 允许任意 id。
- **非尾段且 `arc ∈ {arch, rise}`**：**1.04**（推进感；模板里 B 段是对比/峰值段，rise 曲式的 A' 段也在推进）。
- **其余**：1.0。
- **无 sections 的旧计划**（旧项目 JSON）：最后 1/4 曲长从 1.0 缓降到 **0.85**。
- 越界/脏输入：夹取到 `[0.8, 1.04]`，`bar` 非法取 0。绝不绝不抛错（与 `intensityTarget` 同约定）。

### Player 顺序游标

- `start()` 重置 `_cursorBeat = 0`、`_cursorSec = this._t0`。
- `_enqueueBar(bar)`：期望小节起点 `bar.index * meterNum`；与游标一致时用 `barStartSec = _cursorSec`、`spb = secPerBeat / mult`，音符 `t = barStartSec + n.startBeats * spb`，游标推进 `meterNum * spb`；**不一致（乱序/缺口，不应发生）时回退到原线性映射**，防御性路径，记入注释。
- 暂停/继续语义不变：映射只依赖 `_t0` 与每小节时长表，不依赖真实时间流逝，AudioContext 冻结后自动对齐。
- `barMarks` 的时间同样来自游标——UI 的小节边界与音频严格同源。
- 决策管线深度（AHEAD_BARS=2）不变：乘数由 plan 决定，不依赖决策结果。

### MIDI 导出

- `exportMidi(records, { bpm, meterNum, tempoMults })`：`tempoMults` 是每小节乘数数组（可省略 = 现行为不变）。track0 在每小节 tick（`bar * meterNum * TPQN`）写 `FF 51` 事件，`usPerQuarter = round(60000000 / (bpm * mult))`；与基准相同的乘数跳过（文件更小），t=0 的基准 tempo 始终写。

### 明确不做（YAGNI，记录取舍）

- 工作室回放保持恒速：DAW 惯例是编辑视图恒速预览；工作室的 BPM 输入框就是速度的事实源。MIDI 导出仍带曲线（编曲的完整意图）。
- 演奏指示（director note）不接入速度：速度是**系统二（计划）**的领地，导演指示当前只影响强度与织体密度；混入会让「计划 vs 临场」的边界变糊。
- 计划卡/张力带的 rit. 可视化留给轮次 21（前端轮）。

## 测试计划（TDD：先红后绿）

1. `candidates.test.mjs`：`tempoMultAt` —— 尾段单调下降且 `mult(段尾) ≈ 0.8`；`arch/rise` 非尾段 = 1.04；`flat` 段 = 1.0；无 sections 的旧 plan 最后 1/4 < 1；越界 bar 夹取；恒不抛错（脏输入矩阵）。
2. `player.test.mjs`：假时钟下第二小节时长按乘数缩短（构造 B 段 plan）；游标推进正确（`_cursorSec` = 累计小节时长）；乱序入队回退线性映射不崩溃。
3. `midi.test.mjs`：带 `tempoMults` 导出 → track0 含多个 set_tempo 事件，tick 与 µs 值正确；不带 → 字节与现行为逐位一致。
4. **12 种子决策指标逐位不变**（`analyze-repetition.mjs`）——tempo 不动任何音符，这是「纯渲染层」的直接证明。
