# 请求载荷去冗余 Implementation Plan

> **执行方式**：本会话内联执行（用户明确要求不使用子代理）。

**Goal**：修正 README 里**已经失真**的成本数字，并去掉我在第 2/10/11 轮引入的**重复解释**——同样的信息说两遍是最纯的浪费。

**Architecture**：只动 `questions` 里的 `instructions` 与 `criteria` 文本，**不动任何逻辑、权重或候选集**。决策质量不该因为省 token 而下降，所以只删**重复**，不删**信息**。

---

## 证据

真实渠道实跑（`--real`，64 小节，约 $0.005）后与 README 记载对比：

| | README 记载 | 实测 |
|---|---|---|
| tokens/小节 | ~1100 | **1860（+69%）** |
| 费用/小节 | ~$0.00005 | **$0.000078** |
| 32 小节总价 | ~$0.0016 | **~$0.0025** |

其余真实渠道指标全部守住：和弦种类 10/8（不低于第 2 轮基线 8/8）、相邻重复 旋律 0 / 左手 0、兜底命中 0、候选集驳回 0。

**token 花在哪**（截获一次真实决策的载荷，4673 字符）：

| 部分 | 字符 | 占比 |
|---|---|---|
| `state` | 589 | 13% |
| **`questions`** | **4084** | **87%** |

注意 `state` 里新加的 `form`（49）与 `motif`（31）**合计不到 2%**——我原以为成本涨在 state 上，**猜错了**。真正的成本是 questions 里的文字，而我引入了三处重复：

| 重复 | 浪费 |
|---|---|
| `develop.instructions`（452 字符）已解释五种手法，`develop.criteria`（329）又用完整英文句子解释一遍 | ~130 字符 |
| `function.instructions`（311）与 `function.criteria`（196）同样重复 | ~80 字符 |
| `chord` 描述里「稳定归宿」与「·主功能」是同一件事说两次 | 33 字符/小节 |

**更关键的一点**：和弦描述里的「·主功能」是**完全无用**的——模型已经在第 7 问单独回答了功能，再在和弦选项里告诉它一次是白费。

---

## 做什么

1. `DEVELOP_OPS` 的值压成短标签（语义已在 instructions 里），`composer.js` 的 `develop` instructions 去掉冗余从句。
2. `HARMONIC_FUNCTIONS` 的值压成短标签。
3. `candidates.js` 的和弦描述去掉 `fnMark`（模型已单独回答功能），`ROOT_ROLE` 精简。
4. `develop` / `function` 的 instructions 各压掉约 1/3，去掉与 criteria 重复的措辞。
5. **README 的成本段按实测重写**，并注明成本随决策数与候选描述增长。

**不做**：不删任何信息，不改权重，不改候选集构成。

---

## 验收

- `npm test` 107 全绿（`DEVELOP_OPS`/`HARMONIC_FUNCTIONS` 只改**值**不改**键**，所有校验基于键存在性）
- 载荷字符数下降（本地可测，不花钱）
- 真实渠道复测：tokens/小节 明显下降，且**和弦种类/相邻重复不劣化**（花约 $0.005）
- README 数字与实测一致
