# 修复「移调只移旋律，不移和声」（轮次 22 · 优化）· 2026-09-30

## 做了什么

**一级正确性 bug，存在了整个项目历史**：`keyPc` 的全部消费点只有旋律音阶、Jev state 的 key 标签、UI 显示——`parseRoman('i')` 给出的 rootPc=0 在渲染点被直接当**绝对音高类**用（`lhVoicing` 低音 = 36+C2），所以：

- keyPc=0/7/3（C/G/Eb）三种「调」产出**逐位相同的 C 体系和弦**（取证：`Bb Cm Bb Cm G Cm` 三遍）；
- 用户选调 / LLM 给 keyPc 后**旋律音阶与和弦处于不同调**——旋律强拍锚定的"和弦音"来自 C 体系 chordMidis，真实的不协和；
- Jev 被告知 `key: "G minor"`，候选集却是 C 体系符号——**模型在错误的语境里做选择**；
- README 承诺的「开演前指定 12 个调性之一」对和声无效。

**为什么 19 轮没发现**：默认路径（关键词计划）不给 keyPc → 恒为 0 → 相对度数与绝对音高类恰好相等。只有用户手动选调或 LLM 给调才触发。

## 修复（相对/绝对分离，决策逻辑零改动）

- **唯一介入点 = composer.nextBar 素材化处**：`absPc = (chordP.rootPc + plan.keyPc) % 12`，`chord = { ...chordP, rootPc: absPc, relPc: chordP.rootPc, symbol: chordLabel(absPc, shape) }`。
- **决策层全部锚在 relPc**（不动）：候选集、功能表、疲劳表（改键 `chord.relPc`）、循环锁死（`recentRoots` 改读 `chord.relPc`）、`decision.roman`。
- **渲染层自动修正**（读绝对 rootPc）：左手声位、旋律锚定池、乐句尾吸附、动机承袭池、工作室 barChords、nct 和弦音判定。
- 修复后实测：G 小调 → `F Gm F Gm D Gm`，Eb 小调 → `Db Ebm Db Ebm Bb Ebm`——和声真的随调平移。

## 已知取舍（如实记录）

和弦拼写沿用 `PREFERRED_NAME` 固定惯例：Eb 小调的 bVI 理论拼写是 Cb，现在显示 `B`（同音，钢琴键名也是 B）。完整调号拼写引擎是独立大工程；在「显示 B 弹 B」与「显示 Cb 弹 B」之间选了前者——可读性优先，与轮次 4 的记谱惯例一致。

## 验证

- npm test **134/134**（新增 2 个移调不变量测试）；`node --check` 全过
- 12 种子回归门：chords 9.33 / entropy 2.34 / melody 29.42 / lh 28.33 / madj 0 / ladj 0——**与修复前逐位一致**（默认 keyPc=0 时 absPc === relPc，这是「相对/绝对分离」正确性的直接证明）

## 坑

- 我的第一个测试假设「首小节必是主和弦」——错。seed 42 的 romantic 首小节是 bVII（G 调下为 F，低音 41=F2 恰恰是正确答案）。**断言失败时先怀疑自己的期望值，再怀疑实现**——本项目第 4 轮（拼写脚本）、第 16 轮（统计量）都栽过同一类跟头，这次是第 3 次：`lhVoicing` 的 bass=36+absPc 是唯一的低音声部事实，上三声部不是。
- `??` 对 0 不短路、`||` 会——`relPc: 0`（主和弦）是合法值，任何 `x ?? y` 的读取都安全，`x || y` 会把主和弦当缺失。

## 反思

- **「默认值把 bug 藏起来」是隐藏最深的缺陷形态**：相对/绝对两种语义在默认路径下数值相同，所有测试、所有真实渠道回归都测不到它。审计方法：对每个「X 度数」参数，问「X 的参照系是谁？如果参照系变了（keyPc ≠ 0），哪些消费点会跟着变？」——答案里任何「不变」的点都是嫌疑犯。
- 修复位置的选择：最小介入点选在**语义转换的唯一边界**（素材化处），而不是在每个消费点各自修补。19 轮里反复出现的模式：两种语义并存不可怕，可怕的是**边界不设防**。
