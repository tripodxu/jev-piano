## 我尝试的优化，以及它为什么被否决

我定位了三处**重复解释**并动手压缩：`develop.instructions`（452 字符）已解释五种手法、`develop.criteria`（329）又用完整英文句子讲一遍；`function` 同理；`chord` 描述里「稳定归宿」与「·主功能」是同一件事说两次。

三组真实渠道实测：

| 配置 | 和弦种类 | tok/小节 | 载荷字符 |
|---|---|---|---|
| 改前（原始文本） | 10 / 8 | 1860 | 4673 |
| 全面压缩 | **6 / 7** | 1757 | 4285 |
| 语义挪回 instructions | 7 / 8 | 1845 | 4666 |

**没有免费的 token 可省。** 补回信息就要花 token；砍掉信息就掉音乐质量（−4 种和弦）；「把语义挪个位置」也只换来 0.8%。**已全部回退**（`git checkout` 三个源文件），保留原始措辞。

**一个重要发现**：同 seed 连续两次真实运行结果**完全一致**（和弦种类 7/32、旋律 28/32、左手 27/32，两次相同）。这推翻了 MEMORY 里「真实渠道非确定性」的旧判断——**至少在当前配置下模型是可复现的**。这意味着真实渠道的数字是**真实差异，不是采样噪声**，也让「提示词措辞会移动 ±2 种和弦」这个结论可信。

## 反思

- **这是一轮「优化失败」的诚实记录**。我定位到了真问题、找到了冗余、动手做了，然后被自己的测量否决并回退。**回退不是浪费——把「压缩提示词省 token」这条路证伪，本身就是结论**，而且它阻止了一次会悄悄降低音乐质量的改动。

- **「真实渠道非确定性」这条 MEMORY 旧判断需要修正**。它来自第 1 轮（那时只有 6 问、8 个候选）；现在七问、九候选、曲式信息都进了 state，行为变得更收敛。**长期记忆里的结论也有保质期。**
