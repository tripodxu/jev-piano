## 起因

界面上的标记已经很多：功能轨四色 + 发展手法字 + 断路器刻线/缺口 + 段落虚线 + 动机卡 + 张力带 + 契合度带 + 非和弦亮边。**问题不是不够，是用户看不懂它们意味着什么。**

本轮**不新增任何可视化**——缺的是读法，不是数量。再加一个可视化来解释可视化是最容易走的弯路。

## skill 的硬约束（决定了做法）

- **Context Over Ceremony**：在使用现场教，不一上来倾倒
- **NEVER overwhelm with information upfront（progressive disclosure）**
- **Don't show same onboarding twice — track completion and respect dismissals**
- **尊重用户智力**：不啰嗦

所以：**不做**首访弹窗、**不做**新手教程模式。只做「可选的 ? 抽屉 + 行内图例 + 记住已关闭」。

## 做了什么

1. **图例抽屉**（顶栏「?」）：列出界面上**每一个**标记——色块/形状 + 名称 + 一句话含义，分 4 组（和声功能 / 发展手法 / 断路器与守卫 / 结构 / 分析读数）。
   - **数据驱动**：`LEGEND_ITEMS` 与真实标记同源。**标记改了而图例没改，比没有图例更糟**——所以有测试守覆盖面。
   - 关闭状态存 localStorage（`legendHintOff`），但**「?」按钮永不消失**，随时可重开。
2. **使用现场的图例**：功能轨下方原有的「主/下属/属/色彩」行内图例**就地补上** 承/模/倒/装 与一个「这些标记是什么？」链接。`onboard` 说「teach when users need them」——行内就是「现场」。
3. **工作室空状态补「为什么值得」**：`onboard` 的空状态三要素（这里会出现什么 / 为什么值得 / 怎么开始），原来只有前两条。
4. **收紧工作室提示文案**：一整段墙文改成两行短句。

## 反思

- **`LEGEND_ITEMS` 的测试是本轮最有价值的一行代码**。它断言图例必须覆盖每一个真实标记——这让「图例与标记脱节」从一个隐患变成一个会红的测试。**凡是靠人肉维护的对应关系，都该有一条测试。**
- **「不做」比「做」更难。** 这个界面上再放一个大图例面板很容易、看起来也很有诚意，但它恰好违反 `onboard` 的每一条。做减法的代价是要克制住「再多解释一点」的冲动。
- **我又一次在插入代码时切断了相邻声明**（`DEV_ZH` 被劈成两半、`FN_ZH` 触发 TDZ）。两次都是同一个模式：**按字符串锚点插入而不看上下文**。这类错误 `node --check` 都能抓到，但更省事的做法是先读一眼插入点两侧。
- **测试又写错一次**：`fnLabel` 接收的是功能 id（`'T'`），我当成接收 bar 对象包了一层，断言立刻失败。**函数的签名就是它的文档**，写调用前先看一眼定义。
