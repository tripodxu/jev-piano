# 2026-09-28 · 和弦拼写（降号侧）（迭代轮次 4 · 优化）

> 计划：[../superpowers/plans/2026-09-28-chord-spelling.md](../superpowers/plans/2026-09-28-chord-spelling.md)

## 起因

MEMORY 任务板上挂了许久的「和弦显示升/降号美化（C minor 的 Ab 显示为 G#）」。第 2 轮引入和声功能层后这条变得更显眼——色板开始大量产出 `bVI`/`bIII`/`bVII`，于是界面上、决策日志里、功能轨里都印着 `G#`。

动手前先量（一次性取证脚本，跑完即删）：浪漫小调 32 小节里，**14 小节（44%）拼写错误**——C 小调出现 `G#×6 A#×3 D#×4`，正确应为 `Ab Bb Eb`。这不是审美问题，是**记谱错误**：钢琴家看到 `G#` 会弹出不协和的音。

## 做了什么

`chordLabel` 从绝对音高类 `NOTE_NAMES`（永远升号）改为固定的**音级拼写约定表** `PREFERRED_NAME`：

```js
['C', 'Db', 'D', 'Eb', 'E', 'F', 'Gb', 'G', 'Ab', 'A', 'Bb', 'B']
```

**不改函数签名**——这是本计划成立的前提。两个调用点（`candidates.js` 的候选 label、`composer.js` 的 `bar.chord.symbol`）都零改动。之所以能不改签名，是因为 `STYLES` 里所有带 `b` 前缀的罗马数字恰好就是 1/3/6/8/10 这五个音级，新约定与内核的记谱天然一致。

**关键区分：`midiName` 保持升号不动。** 它标的是**琴键的物理键名**——钢琴上没有 Ab 键，只有 G# 键，`renderKeyboard` 的 title 也在用它。和弦名是**和声记谱**，键名是**物理事实**，两者不能混。已加单测锁住这条边界。

## 验证

- `npm test` 74 → **76**，全绿。TDD 红绿实跑（旧实现 `chordLabel(8,'')` 返回 `'G#'`，测试立即失败）。
- 端到端：C minor 标签变为 `Ab×6 Bb×3 Eb×4`，和弦序列 `Ab Fm Ab Ab7sus4 Cm Dm7b5 Bb Eb …`，**脚本输出里已无任何升号残留**。
- 不回归：`unique_chords` 仍为 9（拼写只改显示文本，符号数不变——若变了说明改动泄漏进逻辑），`interval_entropy` 2.85、旋律/左手相邻重复均 0。
- 新增单射性测试：12 个音级拼写不得重名。

## 反思

- **我的取证脚本第一版自己错了。** 它按**根音**分类「降号调」（`{1,3,6,8,10}`），于是把 **C minor 判成升号调**、报告「0 错误」，实际 14/32 全错。**C 小调有三个降号，本身就是降号调。** 是脚本输出的「0/32」和肉眼可见的 `G#` 互相矛盾才让我回头查。教训：**测量工具的错误比被测对象的错误更难发现，因为它看起来正是你要的答案。**
- **修复后又出现同一个陷阱。** 改完再跑脚本，它报「14/32 错误」，列着「显示 Ab 应为 G#」——这次是脚本的期望值过期了。我差点反过来把正确实现改回去。**一个已经写好、跑得动、给出具体数字的脚本，最容易让人盲信。** 判断脚本是否可信，要看它的假设有没有随改动一起更新，而不是看它报了什么。
- **固定约定 vs 按调号切换**：本可以传 key 进去做「按调号自动选择」，但那样每次调用都要带调、且在 enharmonic 调（如 Gb vs F#）上仍有歧义——项目自己的移调下拉框就把 `1` 写成「C# / Db」，说明这个歧义是真实存在的。固定约定表在所有常用调里都正确、无歧义、少一个参数。**能少一个状态就少一个状态。**
