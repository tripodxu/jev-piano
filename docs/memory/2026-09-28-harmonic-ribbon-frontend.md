## 做了什么

### 1. 和声功能轨（Harmonic Function Ribbon）——本轮核心

第 2 轮给内核加了一整层和声语义（T/S/D/Tp 功能、两条断路器、归因字段），**UI 零展示**。这违反项目自己的承诺「每个音符都能溯源到一条决策」——用户看不见功能层。

现在和弦区与下落音符之间多了一条横向功能轨：每个已演奏小节一格，按功能着色（T 黄铜 / S 冷青 / D 猩红 / Tp 降饱和黄铜），随演奏向右推进，最新一格 `aria-current`。断路器状态直接画在格子上——`loopLocked` 顶部一道细刻线（"这里被切断"）、`rejected` 右端一个缺口（"模型越界被驳回"）。决策日志每行也加了同色的功能徽章，两处共用一套变量，用户在日志与功能轨之间能建立直觉。

**为什么用 DOM 不用 canvas**：只有 18 段，DOM 免费换来可访问性、hover 提示和 CSS 变量配色；项目已有一个 canvas，不该再开第二个。

## 反思

- **detector 报的不是 bug，是变量解析的假配对；但它漏掉了我自己的真 bug。** 它报 `low-contrast: #ece4d4 on --text-dim = 1.9:1` 共 37 次，可这两个变量在真实渲染里从不同时出现为「前景/背景」——是 CSS 变量解析把值配错了。我用数值核实了全部真实配对，5.1:1~16:1 全过。**但我自己写的 `.fn-chip` 真有一处 FAIL：深字 `#1a140c` 压在 `--fn-D` 上只有 4.37:1，低于 4.5:1——detector 37 条噪声里把它盖过去了。** 教训：自动检测器给的是**线索**，不是结论；真正的门槛要自己算一遍数。
- **压暗 vs 提亮，我第一次改反了。** 看到 4.37:1 FAIL 后我下意识把背景压暗（#c85a4a → #b8493a），结果更糟（3.53:1）——深字配深背景必然更差。第二次才想明白要提亮。**改数值前先想清楚哪个变量是前景、哪个是背景。**
- **基线对比差点又骗我一次。** 第一次跑 baseline-diff 时前后都是 53 条、分布一模一样，我差点直接写"零新增"。但告警里的十六进制值暴露了矛盾：baseline 跑的是 stash 后的旧文件，却仍报我新改的 `#b3a892`。回查才发现是我自己的对比脚本把 AFTER 的文件读了两遍。**同一个数字出现两次不等于结论成立，要找一个能证伪的细节去戳它。** 这和第 2 轮「指标相加掩盖失效部位」是同一类错误。
- **保留下来的 52 条我选择不改，并写清理由**：琴毡木纹的 `repeating-linear-gradient` 是木头本身；和弦字上的零偏移黄铜光晕是**舞台顶光**——craft-floor 明确「已确立的视觉世界优先于本清单」；面板的 `1px 边框 + 40px 模糊阴影` 判为通用启发式误报（有偏移的柔和投影是暗底上浮起面板的正常做法）。改这些会变成"把作品改成检测器喜欢的样子"，那不是精修。
